## 项目：在线文件管理系统（A 公网 / B 无公网 / C 网页操作）

**需求已确认**：A 有公网 IP 作中枢；B 主动外连 A 建立长连接；C 通过 A 的前端页面控制 B 上传文件到 A，并管理 A 上的文件（删除/下载）。用户确认此复述准确，细节待补充。

**关键洞察**：
- B → A 传文件不需要隧道（B 出站 HTTPS 即可），只有 A→B 的"取件指令"需要反向长连接。frp 只在需让 C 直连 B 上服务时才必要。
- 市面上无开源项目同时覆盖「反向接入 + 远程取件 + 集中在 A 落盘管理」三件事。

**调研结论（详见 文件管理系统_参考项目调研.md）**：
- 架构最同构：MeshCentral（agent 外连、Files 页可浏览/上传/下载/删除，但文件只中转不落盘）、Tactical RMM（同源加强）、UrBackup（唯一真正落盘，但是快照语义）
- 组件拼装：指令通道用 chisel/rathole/frp；A 端管理用 FileBrowser Quantum / copyparty / dufs
- **重要**：原版 filebrowser/filebrowser 已于 2026 年归档（JWT 不可吊销 + 命令执行漏洞），须改用 gtsteffaniak/filebrowser（Quantum）

## 第三轮：用户确定技术架构

**用户已定的架构**：A↔B 建立 WebSocket 做控制通道，B 按情况选 HTTP 或 socket 上传，后续还要支持 A 向 B 下发实时指令。

**给出的参考优先级（见文档第九章）**：
- 必读三个：remote-machine-access（控制协议+沙箱）、MeshCentral（单条长连接上混跑指令与文件的传输设计）、copyparty（HTTP 分段断点续传）
- 按栈选读：PowerConnect（Node 全栈）、FileBrowser Quantum（A 端管理 API）、UrBackup（落盘存储布局）、chisel（SSH over WebSocket 的 channel 多路复用）
- 不要看：croc（一次性传输无常驻）、Tailscale（组网层无关）、Tactical RMM（MeshCentral 超集，重复）、frp/rathole（端口映射模型与"不暴露 B 端口"相反）

**关键设计结论**：一条 WebSocket 同时跑实时指令和大文件流必然互相阻塞（心跳延迟→误判离线、背压拖死指令队列）。解法二选一：数据单开一条连接，或做多路复用（smux/yamux/SSH channel）。建议先定这一点再定其他。

## 第四轮：技术栈确定，产出实施计划书

**技术栈**：A 端 FastAPI + Vue3；B 端 Python agent；Python 侧统一 uv 管理。

**精读 remote-machine-access 源码后的关键收获**（docs/HANDOFF.md + shared/protocol.py + shared/security.py + agent/main.py）：
- 单写者原则：只有 send loop 能调 websocket.send()，并发 send 会交错帧且间歇性失败
- Futures keyed by message id + 超时，否则挂起请求永久泄漏
- 队列满不能阻塞也不能无界；指令队列与遥测队列必须分开
- 协议放共享模块，改协议在 import 期报错
- CommandName 封闭枚举 —— 即使 relay 被攻破，agent 能力面有限
- Sandbox.resolve() 在 check 之前；token 用 hmac.compare_digest
- 它承认的洞：run_command 的参数绕过 ALLOWED_PATHS（cat /etc/passwd 可读全盘）→ 本系统直接不实现命令执行

**计划书核心决策**：
- 控制走 WS、数据走 HTTP 分片（不是"按情况"，而是按大小+是否续传路由）
- 进度的唯一真相在 A（A 知道收到第几块），B 不重复上报
- C 端用服务端 session + HttpOnly Cookie（不用无状态 JWT）—— 顺带让 SSE 能鉴权（EventSource 不能带 header）
- A 侧下载只吃 file_id 不吃路径 → A 侧无路径穿越面
- 磁盘文件名用 uuid，原始名只存库
- **uv 管不了 Vue**（npm 依赖），用 justfile 统一入口，这是工具边界需向用户说明

## 第五轮：约束确认 + 落地 M0/M1

**用户确认的约束**：C 单人、B 单台、B 生产 Linux 但测试必须在 Windows（→ 必须跨平台）、文件从几 MB 到几 GB。

**由此产生的设计改动**（已写回计划书第十三、十四章）：
- 单用户 → 不建 users 表，argon2 哈希放配置；sessions 表保留以支持吊销
- 几 GB 文件 → 落盘改为**预分配单 .part + 按偏移写入**（峰值 1x 空间，而非每块一文件的 2x）

## 第六轮：用户纠正了一处混淆（重要）

用户指出：pwrite 是写文件用的，B 只读，Windows 不该有写权。

**我确实把两件事混了**：偏移写入发生在 **A 上**（组装 staging 分片），不是 B 上。原文写成"Windows 没有 os.pwrite"容易被读成 B 需要写权限。

**修正结论**：既不用 `os.pwrite` 也不加锁 —— 每次写块**独立开句柄** `open("r+b")` → `seek` → `write` → close，各句柄持有独立文件位置，天然不冲突，两平台一致。理由不是"Windows 没有 pwrite"，而是"不需要平台分支"。已写回计划书。

**新增澄清**：要区分"写权限"与"读被占用"。Windows 上只读也会失败：(a) 文件被独占打开（Excel/Ollama .pst）→ `file_locked`；(b) ACL 无读权限 → `forbidden`。Windows 共享模式由首个打开者决定，对方独占时无解，只能报错。另：B 唯一会写的是自身日志（不在共享根目录内）。

**B 只读三层保证**：命令枚举无写操作 / 只用 "rb" / 沙箱无写入入口。计划加架构测试扫描 agent 源码断言无写模式。
