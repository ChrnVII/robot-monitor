# 在线文件管理系统 · 实施计划书

> 技术栈：A 端 FastAPI（backend）+ Vue 3（frontend）；B 端 Python。两个 Python 项目完全独立（无 workspace、无 path 依赖），线上协议在两端各一份、由契约样例与源码比对保持一致。
> 核心架构：A↔B 一条 WebSocket 控制通道；B→A 文件传输走 HTTP；C 只访问 A。

---

## 一、范围

### v1 要做

| 能力 | 说明 |
|---|---|
| B 反向接入 | B 主动外连 A，注册、保活、断线自动重连 |
| 目录浏览 | C 通过 A 查看 B 上指定根目录内的文件树（走控制通道，10s 超时） |
| 按需取件 | C 勾选 B 上的文件，创建任务，B 分片上传到 A，可断点续传 |
| A 端管理 | C 在 A 上浏览、搜索、下载（支持 Range）、删除（进回收站） |
| 状态可见 | 节点在线状态、任务进度、失败原因，实时推给 C |
| 双套鉴权 | C 的会话 Cookie；B 的设备 Token（可吊销） |

### v1 明确不做

- **B 上的删除/重命名/写入**——B 是只读源，能力面越小越安全
- **任何命令执行**——参考项目里 `run_command` 被证实能绕过路径沙箱（`cat /etc/passwd` 就能读全盘），这是它自己文档承认的洞。本系统直接不提供这个能力
- 多租户、配额计费、秒传去重
- 实时指令下发（协议预留了消息类型，v1 只实现心跳，不做业务指令）
- C 向 B 反向推送文件

## 二、从参考项目提炼的结论

这一节是计划书里最该先看的部分，每一条都直接改变了下文的设计。

| # | 来源 | 结论 | 落到哪里 |
|---|---|---|---|
| 1 | remote-machine-access | **单写者原则**：只允许一个 send loop 调用 `websocket.send()`。两个协程并发 send 会交错帧、破坏流，且失败是间歇性的，最难查 | A 的 hub 与 B 的 client 各有一个 outbox + send loop |
| 2 | 同上 | WebSocket 没有请求/响应配对，必须自己用 `id` + `Future` 做关联，并给每个 Future 加超时，否则挂起的请求会永久泄漏 | `hub.py` 的 `pending: dict[str, Future]` |
| 3 | 同上 | **队列满时不能阻塞，也不能无界**。阻塞会拖死整个事件循环，无界会 OOM | 指令队列与遥测队列**分开**：指令有界但阻塞等待，遥测满了直接丢 |
| 4 | 同上 | 消息形状必须只有一处定义，两端不能各自理解。**实施时改成：两端各持一份相同实现，用契约样例 + 源码比对钉住一致**（比抽独立包少两个 path 依赖） | `protocol.py`×2 + `contract/` |
| 5 | 同上 | 命令用**封闭枚举**，B 拒绝一切未列举的命令。即使 A 被攻破，B 能做的事也是有限集合 | `CommandName` |
| 6 | 同上 | 路径沙箱必须 `resolve()` **之后**再校验。否则 `~/share/../../.ssh` 能骗过字符串比较，软链接能指向全盘 | `sandbox.py` |
| 7 | 同上 | token 用 `hmac.compare_digest`，不用 `==`。时序侧信道足以逐字符还原 token | `auth.py` |
| 8 | 同上 | 大文件传输与指令共用一条 socket 会互相阻塞，且 B 的文件 IO 若是同步的会卡住心跳 | **控制走 WS，数据走 HTTP**；B 侧文件 IO 全部 `asyncio.to_thread` |
| 9 | MeshCentral | 文件传输与指令共存需要显式隔离与背压，不能顺其自然 | 见第 8 条，用双通道从根上规避 |
| 10 | filebrowser（已归档） | 自包含 JWT 无法吊销，登出/改密后旧 token 仍有效 | C 端用**服务端 session 表 + HttpOnly Cookie**，不用无状态 JWT |
| 11 | copyparty / up2k | 分片 + 逐块校验 + 服务端记录已收块，才能断点续传；块大小要自适应 | 上传协议取 `total_chunks` + `received[]` |
| 12 | UrBackup | 快照语义（"某天某时的版本"）和文件池是两种产品。要文件池就别照抄它的目录结构 | 存储按 `agent_id/file_id` 平铺，不做版本快照 |
| 13 | 我自己踩过的 | Starlette 的 `UploadFile` 超过 1MB 会落盘临时文件；直接 `await file.read()` 会把整个文件拉进内存 | 上传一律走 `request.stream()` 或分片端点，不用表单上传 |

## 三、总体架构

```
        ┌──────────────────────────────────────────────┐
        │                 A（公网服务器）                │
        │                                              │
        │   Vue 3 静态产物 ── 由 FastAPI 托管            │
        │   FastAPI（单 worker）                        │
        │     ├─ /api/*        给 C 用（Cookie 鉴权）    │
        │     ├─ /ws/agent    给 B 用（Token 鉴权）      │
        │     ├─ /internal/*  给 B 上传用（Token 鉴权）  │
        │     └─ /api/events  SSE 给 C 看实时状态        │
        │   SQLite + storage/{files,staging}            │
        └───────┬──────────────────────────┬───────────┘
                │ ① WSS 控制通道            │ ② HTTPS 分片上传
                │ （B 主动拨出，常驻）        │ （B 主动发起）
        ┌───────┴──────────────────────────┴───────────┐
        │              B（内网电脑，无公网 IP）           │
        │   agent：outbox/send loop、指令分发、沙箱      │
        └──────────────────────────────────────────────┘
                                ▲
                                │ HTTPS
                        ┌───────┴────────┐
                        │  C 浏览器        │
                        └────────────────┘
```

### 整个设计的不变量

**B 永远是连接的发起方。** 控制连接是 B 拨出，上传也是 B 发起。A 只负责"告诉 B 去传哪个文件"，从不需要主动连 B。这一条决定了：

- 不需要任何隧道或端口映射（frp/rathole 在这个架构里是多余的）
- 防火墙只需要放行 B 的出站 443
- 未来做 A→B 的文件下发时，也应该是 A 下发"去哪里拉"的指令、B 主动 GET，而不是 A 反向推流

### 为什么控制走 WS、数据走 HTTP

你原本的想法是"B 按情况选 http 或 socket"，建议把它变成**规则**而不是**判断**：

| 场景 | 通道 | 理由 |
|---|---|---|
| 指令、心跳、状态、进度 | WS | 小消息、低延迟、需要 A 主动推 |
| 文件上传/下载，>1MB | HTTP 分片 | 可断点续传、可并发、可被 Nginx 接管、失败可单块重试、不占用控制连接 |
| 极小文件（<64KB，如配置、截图） | 可走 WS 内联 base64 | 省一次握手；但要有大小上限，否则会堵住指令通道 |

判据是**大小 + 是否需要续传**，不是"看情况"。这样任何一条指令的行为都是可预期的。

## 四、工程结构

两个 Python 项目完全独立，不是 workspace：各自有 `pyproject.toml`、`.venv`、
`uv.lock`，没有 path 依赖，可以单独 clone、单独 build、单独部署。

线上协议不抽独立包，而是在两端各放一份 `protocol.py`，**要求逐字节相同**，
由两道测试兜住（见 4.5）。这是用 200 行重复换部署独立：给 B 装 agent 只要一个
wheel，改协议时也不会漏掉第三个项目。

A 端的 backend 与 frontend 是两个技术栈，物理上放在同一个 `server/` 下，
但构建与运行完全解耦：frontend 出静态产物，backend 只负责托管。

```

├── dev.sh                               # 统一入口（uv 管不了 npm，见 4.3）
├── contract/

├── server/                              # A 端

│   │   ├── pyproject.toml
│   │   ├── src/filebridge_server/
│   │   │   ├── main.py                  # create_app + lifespan + 静态托管
```

### 4.1 为什么用 `src/` 布局

uv 的构建后端默认在 `src/` 下找包。如果包目录与 `pyproject.toml` 平级（扁平布局），必须额外写 `[tool.uv.build-backend] module-root = ""`，否则项目**不会**被装进 venv，`[project.scripts]` 也找不到入口点，最后你会不自觉地退回去用 `.venv/Scripts/python.exe -m xxx`——那等于绕开了 uv。用 `src/` 布局可以完全避开这个坑。

### 4.2 两份 pyproject 的关键片段

`agent/pyproject.toml`——没有 workspace、没有 path 依赖，可以单独 build：

```toml
[project]
name = "filebridge-agent"
requires-python = ">=3.12"
dependencies = ["websockets>=13", "httpx>=0.27", "pydantic>=2.8"]

[project.scripts]
filebridge-agent = "filebridge_agent.main:main"

[build-system]
requires = ["uv_build>=0.12,<0.13"]
build-backend = "uv_build"
```

`server/backend/pyproject.toml` 同理，只多几个 Web 依赖。它唯一的一条 path 依赖
是**测试用**的 agent——端到端测试要驱动一个真实的 agent，但它不进运行时依赖：

```toml
[tool.uv.sources]
filebridge-agent = { path = "../../agent", editable = true }

[dependency-groups]
dev = ["pytest>=8.0", "pytest-asyncio>=0.24", "httpx", "websockets", "filebridge-agent"]
```

### 4.3 一个必须说明的边界：uv 管不了 Vue

**uv 只管理 Python 生态，没有也无法管理 npm 依赖。** 前端的 `vue / vite / pinia` 必须由 Node 工具链装。这是工具边界，不是可以绕过的设计选择。

处理方式：根目录放一个 `dev.sh` 作为统一入口，前端产物由 FastAPI 直接托管，开发时用 Vite 的 proxy 转发到后端。

```bash
./dev.sh serve --reload                   # A 端
./dev.sh web                              # 前端 dev server（5173，proxy 到 8000）
./dev.sh agent --server ... --token ...    # B 端
./dev.sh build                            # 产出 server/frontend/dist
./dev.sh test                             # 两个项目一起跑
```

用 shell 脚本而不是 justfile：`just` 不是标配，装不上就等于没有入口；
bash 在任何目标环境（Linux 服务器、开发机的 git bash）都有。

生产部署时 `web/dist` 已经构建好，A 上只需要 Python 运行时。

### 4.4 B 端的交付方式

B 上不应该要求装 git 和源码。做法：

```bash
uv build --project agent -o dist/            # 只有一个 wheel，agent 自包含
# 拷到 B 上
uv tool install ./filebridge_agent-0.1.0-py3-none-any.whl
filebridge-agent --server https://a.example.com --token xxx --root /srv/share
```

`uv tool install` 会给 agent 建独立环境，不与系统 Python 冲突。

只有一个 wheel，是因为协议就在包内（`filebridge_agent/protocol.py`）。
这是不抽共享包最直接的好处：B 上的安装步骤只有一步。

### 4.5 协议为什么复制两份，以及怎么防止漂移

抽第三种方案是独立 `protocol` 包，实施时做过一版，最终拆掉，因为它的成本是可数的：

- 两个 `pyproject.toml` 各写一条 path 依赖
- 给 B 装 agent 要装两个 wheel（协议包的 METADATA 里只有包名，B 上必须能解析到）
- 改一行注释要动第三个项目、跑第三次 `uv sync`

而这个包总共 200 行、5 个命令、11 个错误码，稳定度极高。于是改成两端各放一份
`src/.../protocol.py`，**要求逐字节相同**。

复制唯一的新风险是漂移，用两道测试兜住，两边都跑：

| 测试 | 挡住什么 |
|---|---|
| `test_protocol_copy_is_identical` | 直接比对两份源码字节。改一边忘另一边 → 红 |
| `test_golden_frames_match` | 两端都读 `contract/protocol-frames.json`，解析与序列化结果必须与样例一致。两边都改错但改得不一样 → 也红 |

第二道测试用的是"黄金样例"：8 个覆盖各消息类型的完整帧 + 3 个必须被拒的畸形帧。
它同时钉住字段名、`exclude_none` 的裁剪行为、枚举的落值形态——只测"能解析"不够，
序列化侧改了字段名照样能解析旧帧。

改协议的标准顺序：**先改契约样例 → 再改两份 `protocol.py` → 跑 `./dev.sh test`**。

## 五、协议设计

### 5.1 帧结构

JSON，单帧形如：

```json
{"v":1,"type":"command","id":"c9f1a2","command":"list_dir","payload":{"path":"","limit":200},"ts":1761033600.1}
```

- `v` 协议版本，不匹配直接拒绝并让 agent 提示升级
- `id` 请求与响应共用，用于配对
- `type`：`hello | command | result | event | ack | error | status`
- 为空的字段不序列化，保持帧小、日志可读

### 5.2 命令枚举（v1，封闭）

| 命令 | 方向 | 说明 |
|---|---|---|
| `ping` | A→B | 应用层心跳，回应 `pong` 带时间戳 |
| `list_dir` | A→B | 列目录，支持 `limit` + `cursor` 游标分页 |
| `stat_file` | A→B | 上传前确认文件存在、大小、mtime、是否可读 |
| `start_upload` | A→B | 派发上传任务，附 `upload_id`、目标 URL、块大小 |
| `cancel_task` | A→B | 取消进行中的上传 |

**没有** `delete`、`write`、`run_command`。B 是只读源。

关于"封闭"落在哪一层，实施时改过一次：`Message.command` 在线上是**裸字符串**，
不是 `CommandName` 枚举。原因是如果把它声明成枚举，老版本 B 收到一个它不认识的
新命令时会在 pydantic 校验阶段就失败 → 整条连接被关掉，而正确行为是回一个
`unknown_command` 让 A 知道"这台机器不会做这件事"。

结论：**解析宽松、执行严格**。`Message.parse` 接受任意 64 字符以内的命令名，
`handlers.dispatch` 对照 `AGENT_ALLOWED_COMMANDS` 拒绝一切未列举的。这样封闭性
保住了，同时协议向前兼容。

### 5.3 错误码

`unauthorized / agent_offline / unknown_command / forbidden / invalid_arguments / file_not_found / checksum_mismatch / timeout / rate_limited / internal`

每个错误都必须有明确 code，不能只回一个字符串——前端要按 code 决定是否展示"重试"按钮。

### 5.4 一次取件的完整时序

```
C                A                          B
│  POST /tasks    │                          │
│────────────────>│  建 task(pending)         │
│                 │  stat_file ──────────────>│
│                 │<───────────── result(size)│
│                 │  建 upload(id, chunks)     │
│                 │  start_upload ───────────>│
│                 │<───── ack                │
│                 │  ② PUT /internal/uploads/{id}/chunks/0..n
│                 │<──────────────────────────│  （HTTP，可并发、可中断）
│                 │  ③ POST .../complete      │
│                 │<──────────────────────────│
│                 │  校验 sha256 → 原子 rename → files 表插入
│  SSE task_done  │                          │
│<────────────────│                          │
```

关键点：**进度的唯一真相在 A**。A 知道自己收到第几块，不需要 B 上报进度；B 只在完成/失败时通知。这样避免了 B 和 A 各存一份进度、对不上的问题。

## 六、安全模型

### 6.1 三层，缺一层都不成立

| 层 | 位置 | 措施 |
|---|---|---|
| 鉴权 | A | C：Argon2 密码 + 服务端 session（HttpOnly/Secure/SameSite=Lax）；B：每台一个 token，库里只存 sha256，可即时吊销 |
| 授权 | A | 只接受 `file_id` 下载，**不接受路径**。这样 A 侧根本不存在路径穿越面 |
| 沙箱 | B | `resolve()` 后校验是否在允许的根目录内（Linux 上软链接无需特权即可创建，这一步是必需的） |

### 6.2 双层校验，不是重复

- A 侧：C 提交的 `path` 先进规范化（拒绝绝对路径、拒绝 `..`、按根目录拼接），再下发给 B
- B 侧：拿到路径后独立再做一次 `resolve()` + 前缀校验

为什么两层都要：A 是唯一暴露面，可能被绕过；B 是真正持有文件的一方，必须自己兜底。**绝不能因为"A 已经校验过了"就在 B 上省略**。

### 6.3 几个容易漏的点

- **C 的 Cookie 不能存 localStorage**：SSE 的 `EventSource` 无法携带自定义 header，用 Cookie 是为了让 SSE 能鉴权，顺带避开 XSS 窃取 token
- **B 的 token 走 header 不走 query**：`?token=` 会进 Nginx access log
- **上传端点必须校验 Content-Length 和实际字节数**，两者不符立即断开，否则可被磁盘打满
- **块校验要服务端重算**，不能信客户端传上来的 sha256
- **B 侧不做命令执行**，从设计上消除 RCE 面

## 七、存储设计

### 7.1 磁盘布局

```
storage/
├── staging/{upload_id}.part          # 预分配的空文件，各块按偏移写入
└── files/{agent_id}/{file_id[:2]}/{file_id}   # 已入库
```

- 磁盘文件名用 `file_id`（uuid），**原始文件名只存数据库**。这一条同时解决了：中文/emoji 文件名、重名覆盖、路径穿越、大小写文件系统冲突
- 两字符分片目录，避免单目录十万文件导致 `ls` 卡死
- 上传完成用 `os.replace()` 原子改名，保证"库里有的文件一定完整"

**为什么是单个 `.part` 预分配文件，而不是每块一个文件**：几 GB 的文件如果每块存一个文件，`complete` 时要先拼装，磁盘峰值会到文件大小的 **2 倍**（5GB 文件需要 10GB 空间）。改成先 `truncate(total_size)` 预分配、各块用「seek 到偏移 + write」写入，峰值只要 **1 倍**。代价是 `complete` 时要顺序读一遍算 sha256，5GB 在机械盘上约 30 秒、SSD 上 10 秒以内，可以接受。

**先厘清一件事：这个偏移写入发生在 A 上，不在 B 上。** B 全程只读，从不写自己的磁盘（详见第十四章的只读不变量）。这里写的是 A 的 `storage/staging/*.part`。

A 是 Linux，`os.pwrite` 在这里是可用的：它做带偏移的原子写，多个块并发写同一个 fd 时不用抢文件指针。但用它意味着要为每个进行中的上传维护一个长生命周期的 fd，还要处理会话过期时的关闭与泄漏。

结论是**先用「每次写块独立开句柄」**：`open(path, "r+b")` → `seek(offset)` → `write(data)` → 关闭。不同句柄各自持有独立的文件位置，天然互不干扰。每次 1–8MB 配一次 open/close，开销相对数据量可以忽略，也不需要 fd 记账。

如果后续压测发现 open/close 成为瓶颈（并发上传很多时），再改成常驻 fd + `os.pwrite`——那是一次局部替换，不影响协议。

### 7.2 表结构

```sql
-- 单用户部署，不建 users 表：管理员账号和 argon2 哈希直接放配置
sessions(id, token_hash, expires_at, created_at)   -- 可吊销
agents(id, name, token_hash, os, agent_version, roots, last_seen, online, created_at)
tasks(id, agent_id, type, src_path, status, file_id, error, created_at, updated_at)

        total_chunks, received_json, sha256_expected, status, created_at, updated_at)
files(id, agent_id, orig_name, size, sha256, stored_path, created_at, deleted_at)
```

`agents` 表虽然只有一行，仍然保留 `agent_id` 字段——不是因为预期多节点，而是因为将来重装 B、换机器时，token 要能独立吊销并重建，不能把身份写死在代码里。

`received_json` 存已收块号数组。v1 用 JSON 够了；单文件上万块时再换 bitmap BLOB。

`deleted_at` 软删除，文件在磁盘上移到 `storage/trash/`，30 天后清理。

### 7.3 任务状态机

```
pending → uploading → verifying → done
   │          │            │
   └──────────┴────────────┴──→ failed
                              → canceled
```

状态只由 A 写，B 通过 HTTP 完成回调或 WS 错误来影响它。任何状态变更都广播 SSE。

## 八、上传协议（断点续传）

参考 up2k 的思路，但简化为四个端点：

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/v1/uploads` | 由 A 内部创建（C 不直接调），返回 `upload_id`、`chunk_size` |
| PUT | `/internal/uploads/{id}/chunks/{n}` | B 上传第 n 块，**幂等**，重传覆盖 |
| GET | `/internal/uploads/{id}/status` | B 重连后查询已收块，用于续传 |
| POST | `/internal/uploads/{id}/complete` | 提交整体 sha256，A 校验后原子落盘 |

- 块大小按文件大小自适应：< 512MB 用 **1MB**，≥ 512MB 用 **8MB**。5GB 的文件切 1MB 块会产生 5120 次 PUT，仅请求和事务开销就很可观；8MB 块降到 640 次
- 每块独立 `PUT`，B 侧 **3 并发**；并发过高会让 A 的磁盘寻道变成瓶颈，反而更慢
- 开始前预检磁盘余量，要求 ≥ `total_size × 1.2`，不够直接拒绝建任务（比传到 90% 再失败体验好得多）
- 会话空闲超 30 分钟自动回收，staging 一并清理
- `complete` 时顺序读一遍算整体 sha256；不符则置 `checksum_mismatch`，保留 staging 供排查，不落盘

**B 重启后如何续传**：B 启动时 `hello` 带上未完成的任务列表；A 对每个 upload 返回已收块。B 从第一个缺失的块继续。这一步是幂等设计的意义所在。

### 9.3 前端的三个坑

1. **`EventSource` 断线后浏览器会自动重连，但不会重放错过的消息**。所以 `task_done` 这类终态事件不能只靠 SSE，重连后要拉一次 `GET /tasks` 对账

## 十、已知坑清单

### A 侧

| 坑 | 后果 | 应对 |
|---|---|---|
| uvicorn 多 worker | 连接注册表在进程内存，多 worker 时 C 连到 worker A、B 连到 worker B，永远找不到对方 | v1 强制 `--workers 1` 并在启动时断言；将来要扩就上 Redis pub/sub |
| `UploadFile` 直接 `await read()` | 整个文件进内存，2GB 文件直接 OOM | 只用分片端点，不用表单上传 |
| 响应中文文件名 | header 只能 latin-1，直接写中文抛 `UnicodeEncodeError` | `Content-Disposition: attachment; filename*=UTF-8''<pct-encoded>` |
| SSE 被 Nginx 缓冲 | 前端收不到实时事件，直到连接关闭 | `proxy_buffering off; proxy_read_timeout 1h` |
| SQLite 并发写 | `database is locked` | `WAL` 模式 + 单连接串行写 + `busy_timeout` |
| Nginx 默认 body 上限 1MB | 8MB 的块全部被 413 打回，且报错位置在代理层，不看日志会以为是客户端问题 | `client_max_body_size 32m;` 且 `proxy_request_buffering off;` |
| Range 支持不确定 | 大文件下载无法续传 | 实施时先 `curl -H 'Range: bytes=0-99'` 验证 Starlette 版本行为，不足则手写 Range 解析 |

### B 侧

| 坑 | 后果 | 应对 |
|---|---|---|
| 同步文件 IO 直接写在协程里 | 阻塞事件循环 → 心跳发不出去 → A 误判离线 → 上传被中断，且现象诡异 | 所有 `open/read/hash` 走 `asyncio.to_thread` |
| 并发 send | 帧交错、流被破坏，间歇性失败 | 单写者：只有 send loop 能碰 socket |
| 重连无退避 | A 重启时所有 B 同时重连，把它再打挂 | 指数退避 + jitter，上限 30s |
| 大文件边读边传 | 内存峰值 | 按块读取，块缓冲区固定 1–8MB |
| 多个任务抢带宽 | 都变慢、都超时 | `asyncio.Semaphore(3)` 限制并发上传 |

### 工程侧

| 坑 | 应对 |
|---|---|
| 扁平布局导致项目没被装进 venv | 用 `src/` 布局（见 4.1） |
| `uv run app/main.py` 触发相对导入错误 | 只允许 `uv run python -m ...` 或 console script |
| 前端被误以为能用 uv 管 | 明确写在 README：前端用 pnpm，`justfile` 统一入口 |

## 十四、B 端平台约束（Linux）

B 的生产环境与测试环境都是 Linux，**不再保留任何 Windows 兼容代码**。盘符、UNC、大小写不敏感、反斜杠分隔符、junction、MAX_PATH、控制台编码、uvloop 可用性这些分支一并移除——少一层平台分支，就少一条常年没人走的代码路径。

这门约束落在代码里是一个**入口门禁**，不是文档里的一句话：

```python
def require_linux(platform_name: str | None = None) -> None:
    name = platform_name if platform_name is not None else sys.platform
    if name != "linux":
        print(f"FileBridge agent 只支持 Linux，当前平台是 {name}。", file=sys.stderr)
        raise SystemExit(2)
```

`main()` 解析完参数就调用它。挡的不是"跑不起来"，而是"看起来能跑"：沙箱在非
POSIX 文件系统上的行为差异（保留设备名 `CON` 会阻塞读线程、NTFS 备用数据流、
尾随空格别名）没有一条被验证过，放它跑等于制造一个没人负责的运行态。

实施中为此**删掉的**唯一一处真正的兼容分支，是 `_run()` 里包住
`loop.add_signal_handler` 的 `except NotImplementedError`（Windows 事件循环不支持
SIGTERM handler）。目标平台之外不保证行为，留着兜底分支反而是在假装支持。

剩下这些是 Linux 上真实存在的约束：

| 约束 | 后果 | 处理方式 |
|---|---|---|
| 只有 `/` 是分隔符 | 反斜杠是**合法文件名字符**，按 `\` 切分会把名为 `a\b` 的文件误判成两级目录 | 协议层只按 `/` 切分，单测钉住该行为 |
| 大小写敏感 | `Report.txt` 与 `report.txt` 是两个文件 | 不做任何大小写归一，直接比较 |
| 软链接无需特权即可创建 | 根目录里一个指向 `/etc` 的软链接就是完整逃逸 | 必须 `resolve()` 之后再判断包含关系；不能只查"是不是链接" |
| 软链接环 / 悬空链接 | `resolve()` 抛 `RuntimeError` / `OSError` | 捕获后转 `forbidden`，不要冒泡成 500 |
| 文件可能在读取过程中被追加 | 日志文件是典型场景：读出的字节数不等于 stat 时的大小 | 上传前后各 stat 一次，不一致返回 `size_changed` |
| POSIX 权限位 / ACL | 无读权限时 `open` 抛 `PermissionError` | 转 `forbidden`，错误信息里带上相对路径 |
| 单文件名 255 字节、路径 4096 | 超长触发 `ENAMETOOLONG` | 相对路径进入沙箱前先做长度校验 |
| 网络挂载（NFS/SMB） | `resolve()` 可能长时间阻塞，拖住事件循环 | 列目录与 stat 放线程池，并设超时 |

**关于分隔符的一个细节**：协议分隔符固定为 `/`（与平台无关），但 `is_within()` 比较的是已经 resolve 过的**真实本地路径**，那里用 `os.sep`。这不是兼容分支——它表达的是"我在比较本地路径，不是在拼线上路径"。在 Linux 上 `os.sep` 就是 `/`，两者完全等价；硬编码 `/` 会让这段判断的正确性依赖于"分隔符恰好相同"这个巧合。

### B 的只读不变量

B 从不写共享目录。这条不靠"写代码时小心"，而靠三层结构性保证：

1. 命令枚举里没有任何写操作——没有 `delete`、`rename`、`write`、`run_command`
2. agent 打开共享目录下的文件只用 `"rb"`，全代码库不出现 `"w"` / `"a"` / `"r+"`
3. 沙箱只提供 `resolve()` 和列目录，不提供任何写入入口

计划加一条架构测试：扫描 `packages/agent/` 的源码，断言不存在写模式打开文件的调用。这类"结构不变量"测试比事后 code review 可靠。

### 读失败的三种情形，不要混为一谈

Linux 上打开中的文件仍然可读（不存在 Windows 那种独占共享阻塞），但读仍可能失败：

- **路径不存在** → `file_not_found`
- **POSIX 权限位 / ACL 不允许读** → `forbidden`，错误信息带上相对路径，方便判断卡在哪个文件
- **读的过程中内容变了** → `size_changed`。日志文件、正在写入的数据库转储都会这样

最后一种最容易被忽略：`stat` 拿到 100MB，实际读到 120MB 才到 EOF——说明文件在上传期间被追加了。上传完成后必须核对**实际读出的字节数与 stat 时是否一致**，不一致就整体失败，而不是把半个文件当完整的交上去。

**B 唯一会写的是它自己的日志文件**，写到 agent 自己的日志目录，不碰共享根目录。"只读"指的是共享目录，不是"整个进程不落盘"。

### 软链接测试的环境依赖

有些文件系统或沙箱环境下，`symlink_to()` 调完并不真的创建链接（Python 不报错，`os.path.islink()` 返回 False）。这种环境里"建个软链接测逃逸"毫无意义，测试必须显式探测并在未建成时 skip——否则会出现"测试通过但其实什么都没验证"的假阳性。

安全判断本身抽成了 `is_within()` 单独做单元测试，不依赖能否创建软链接。那条判断才是真正挡住越界的东西。

### 零配置接入（M9）

上线之后补的一轮改造，目标是让部署少两步手工动作：

| 改动 | 之前 | 现在 |
|---|---|---|
| 管理员密码 | `hash-password` 生成 → 写进 env → 重启才生效 | 首次 `serve` 引导设置；存在库里，`passwd` 随时改，立即生效 |
| B 的凭据 | `issue-token` → 复制 → 贴到 B | 首次带 `--server` 自动注册，token 直接落到 0600 凭据文件 |
| 准入控制 | 只有"手工签发"一条路 | `ENROLL_POLICY=first/open/closed` 三档，`pending` / `approve` / `reject` |

这一轮引入了 `admin_user` 与 `enroll_requests` 两张表、`/internal/enroll` 端点
（HTTP，不动 WS 协议，所以两份 `protocol.py` 不变）。

### 被测试抓到的真实问题（记录在此避免重犯）

1. 早期实现用 `Path.relative_to()` 算相对路径，根目录会得到 `"."` 而不是 `""`，
   让"根目录"在线上出现两种表示。现在 `list_dir` 直接拼相对路径，不再做这种反算
2. `lifespan` 读的是模块级 `settings` 单例而非 `app.state.settings`，导致测试注入的
   临时目录不生效，会往仓库里建 `storage/`
3. `is_within()` 一开始硬编码 `/` 做包含判断，去掉 Windows 兼容后本地直接误判越界——
   内部比较必须用 `os.sep`
4. **`/api/v1/files`、`/api/v1/tasks`、`/api/v1/agents` 一开始没有挂会话依赖**，未登录
   就能读文件列表。单元测试全绿，是端到端那条"匿名访问必须 401"抓出来的。
   教训：安全属性必须用"从外面打进去"的方式测，不能只测函数返回值
5. `Message.command` 原本声明成 `CommandName` 枚举，导致老版本 B 收到新命令时在
   **解析阶段**就炸掉并关连接。改成裸字符串 + 分发时对照白名单后，才真正满足
   "B 拒绝一切未列举命令"这条不变量
6. agent 的 `__version__` 没定义，而 hello 帧要读它——连接在第一帧就抛异常，表现为
   "一直重连、A 侧永远离线"。凡是在握手路径上读的模块级变量，都该有一条测试覆盖
7. 密码搬进数据库后，登录接口**仍然在看环境变量**，导致"密码明明设好了却返回 503"。
   单元测试全绿（它们直接构造 Settings），是端到端验收脚本跑出来的。
   教训同第 4 条：改了配置来源，就要把所有"读配置做判断"的地方找一遍
