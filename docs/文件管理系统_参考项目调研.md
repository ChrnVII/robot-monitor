# 在线文件管理系统 · 参考项目调研

> 需求锚点：A（公网 IP）做中枢，B（无公网 IP）主动外连，C 通过 A 的网页控制 B 把文件传到 A，并在 A 上管理这些文件。

## 一、先明确判定标准

把需求拆成三个可独立评判的能力，才能看清每个项目到底覆盖了哪一段：

| 编号 | 能力 | 说明 |
|---|---|---|
| **① 反向接入** | B 无公网 IP 也能被 A 驱动 | 客户端主动外连、长连接保活、断线重连 |
| **② 远程取件** | C 触发 B 把指定文件送到 A | 浏览 B 的目录 → 选中 → 传输 → 落盘到 A |
| **③ 集中管理** | C 在 A 上浏览 / 下载 / 删除 | 文件长期驻留在 A，可检索、可批量操作 |

**关键判断：市面上没有一个开源项目同时把 ①②③ 做全。** 项目管理类工具做全了 ①② 但不落盘，网盘类工具做全了 ③ 但需要被管理机器自己有公网入口。

## 二、第一梯队：架构同构（agent 主动外连 + 网页管文件）

### 1. MeshCentral —— 匹配度最高

- 仓库：https://github.com/Ylianst/MeshCentral ｜ Apache-2.0 ｜ Node.js
- **架构**：在被控机装 MeshAgent，agent 主动向服务器发起 HTTPS/WebSocket 连接，**无需为每台设备做端口转发**。服务器提供纯 Web 界面。
- **文件能力**：设备详情页有独立的 `Files` 标签，可远程浏览文件系统、上传、下载、重命名、整理、删除，支持拖拽。
- **为什么最像**：B 无公网 IP 这个前提，正是 MeshCentral 的默认工作场景（NAT、家庭路由、企业防火墙后，只需放行出站 HTTPS）。
- **短板**：
  - 定位是远程运维平台，不是网盘。文件页是"运维视角"（单机、单次操作），没有任务队列、没有归档区、没有批量取件。
  - 文件是**流式经过 A 转发给 C**，不在 A 上长期留档。你要的"上传到 A 再管理"需要额外改造。
  - 自带远程桌面 / 终端 / AMT 等一整套能力，对纯文件场景来说偏重。

### 2. Tactical RMM —— 基于 MeshCentral 的加强壳

- 仓库：https://github.com/amidaware/tacticalrmm ｜ MIT ｜ Django + Vue + Go agent
- **架构**：自己的 Go agent 负责接入，文件功能复用 MeshCentral。
- **文件能力**：明确列出 `Remote file browser (download and upload files)`。
- **适合场景**：如果你最终要做成"多台 B、多用户、带权限"的系统，它的权限模型（用户/设备组/角色）可以直接抄。
- **短板**：部署组件多（Django、NATS、MeshCentral、Redis、Postgres），Windows 生态优先，偏重。

### 3. UrBackup —— 唯一真正做到"落在 A 上"

- 仓库：https://github.com/urbackup/urbackup_backend ｜ AGPL-3.0
- **架构**：客户端/服务端模型。开启 Internet 模式后，**B 主动连接 A 的 55415 端口**（无需 B 有公网 IP），A 可以反向驱动 B 执行备份。
- **文件能力**：A 的 Web 界面（默认 55414）可以浏览 B 的备份内容，下载单个文件或整个目录（ZIP，单包上限 4GB），也可以从网页发起恢复任务。
- **为什么值得看**：这是唯一"文件真正沉淀在 A 上、C 再从 A 拿走"的开源实现，而且它处理了互联网模式下的鉴权与断线重连。
- **短板**：
  - 心智模型是**备份快照**，不是文件池。你面对的是"某天某时的版本"，而不是一个可增删的目录树。删除语义、去重策略都和你的需求不一致。
  - C 无法指定"现在把 B 上这个文件给我"，只能等备份周期，或手动触发一次全量扫描。

## 三、第二梯队：用成熟组件拼装（工程落地最省事）

把需求再拆细一层，会发现一个容易忽略的事实：**B 向 A 传文件，根本不需要隧道。** B 直接向 A 的公网地址发起 HTTPS 上传即可（出站方向，NAT 放行）。真正需要"反向通道"的只有一件事——A 把"去取哪个文件"这个**指令**推给 B。

所以最小可行架构是：**一条 WebSocket 指令通道 + B 主动 HTTP 上传 + A 上的文件管理器**。frp 那类端口映射只在"你想让 C 直接访问 B 上跑的服务"时才必要。

### 指令通道（解决 ①）

| 项目 | 定位 | 说明 |
|---|---|---|
| **frp** https://github.com/fatedier/frp | 最成熟的反向代理 | 10 万+ star，TOML 配置，带 Dashboard、TLS、P2P 模式。功能全但偏重，适合以后要暴露多个服务 |
| **rathole** https://github.com/rapiz1/rathole | Rust 轻量替代 | 内存约 5MB，默认 Noise 加密，吞吐高于 frp。只做端口转发，无 HTTP 域名路由 |
| **nps** https://github.com/ehang-io/nps | 带 Web 面板的穿透 | 可视化配置，对"要给 C 一个管理界面"的场景友好 |
| **chisel** https://github.com/jpillora/chisel | 走 HTTP/WebSocket 的隧道 | 只放行 80/443 的网络也能用，支持 SOCKS5。**实现原理最接近你需要的"B 主动外连"** |

### A 端文件管理（解决 ③）

| 项目 | 说明 | 注意 |
|---|---|---|
| **FileBrowser Quantum** https://github.com/gtsteffaniak/filebrowser | 原 File Browser 的活跃分支，单二进制，`config.yaml` 配置，OIDC/LDAP/2FA，SQLite 索引搜索，多源目录 | **原版 filebrowser/filebrowser 已于 2026 年归档**，且遗留 JWT 不可吊销、命令执行等高危问题，不要再用原版 |
| **copyparty** https://github.com/9001/copyparty | 单 Python 文件、零依赖，分块断点续传 + 去重，同时支持 WebDAV/FTP/SFTP，4.6 万 star | 界面偏功能型，配置项多。**断点续传是同侪里最强的**，大文件场景优先 |
| **dufs** https://github.com/sigoden/dufs | Rust 单二进制，约 10.9k star，轻量（32MB 内存），支持 WebDAV 与断点续传 | 功能比前两者少，胜在极简 |

## 四、第三梯队：传输与组网原语（可借鉴，不建议直接用）

| 项目 | 用途 | 对你有用的地方 |
|---|---|---|
| **croc** https://github.com/schollz/croc | 中继服务器桥接两端，PAKE 端到端加密，支持断点续传，可自建 relay | 可借鉴它的"房间 + 短口令"配对思路，用于 B 的首次接入授权 |
| **Tailscale / Headscale** https://github.com/juanfont/headscale | 组网，让 A 拿到一个能直连 B 的虚拟 IP | 如果你不想写隧道代码，这是最快让 A "够得着" B 的办法；之后再挂文件管理器 |
| **Pangolin** https://github.com/fosrl/pangolin | WireGuard 零信任反代，connector 主动外打 | 自带 Web 面板 + SSO + 审计日志，配置比 frp 直观 |
| **sish** https://github.com/antoniomika/sish | 纯 SSH 反隧道（`ssh -R`） | 极端情况下 B 上什么都不用装，有 ssh 客户端即可 |

## 五、GitHub 实测：真正直接命中这个架构的项目

用 GitHub API 做了三轮检索（关键词 → README 精确短语 → 逐仓库验证），结论需要修正：**这个架构在 GitHub 上确实存在，而且不止一个，但全部是 0–64 星的个人项目，没有生产级的。**

### 1. Ferinmtk/remote-machine-access —— 架构吻合度 100%

- https://github.com/Ferinmtk/remote-machine-access ｜ 2 star ｜ Python ｜ **无 LICENSE 文件**
- README 原文：*"Manage a computer at home from anywhere — no port forwarding, no public IP. An agent, a relay, and a browser dashboard."*
- 架构：agent 在 B 上以 **WSS 出站**连到 relay（Docker 部署在 A），浏览器连同一个 relay，**两端从不直连**。README 里那句 *"That inversion is the whole trick"* 说的就是你要的东西。
- 文件能力：`Browse, download, upload, delete — confined to directories you configure`
- **最值得抄的是它的安全设计**：
  - 路径沙箱在 `resolve()` **之后**校验——README 明确指出 `~/shared/../../.ssh` 能骗过字符串比较，软链接能指向磁盘任意位置，且这两个 case 都有测试。
  - token 用 `hmac.compare_digest` 比较，避免时序侧信道。
  - 命令执行走 `create_subprocess_exec` + argv 列表，不经 shell，`ls; rm -rf ~` 直接被拒绝。
- **致命短板**：relay 是"无状态的 broker"，**文件只在浏览器与 agent 之间流式穿过 A，不落盘**。而且没有 LICENSE 文件 = 法律上默认保留所有权利，不能直接商用或二次分发。

### 2. HecreReed/PowerConnect —— 中文、MIT、一体化

- https://github.com/HecreReed/PowerConnect ｜ MIT ｜ Node.js 18+
- 定位：**远程终端 + 文件管理 + 内网穿透一体化**，一键起 frp 或 SSH 隧道。
- 文件能力：目录浏览、下载、可选创建/删除/重命名，**已做路径穿越限制**（限制在根目录内），移动端适配。
- **短板**：它的模型是"**把 Web 服务跑在 B 上，再用 frp 把 B 的 3000 端口映射到 A**"。也就是说 C 访问的是 B 上的页面，文件始终在 B 上，A 只是端口转发。和你要的"文件落到 A 上再管理"不是一回事——但如果你放宽为"只要能用网页管 B 的文件"，它开箱即用。

### 3. tfcenter/tfcenter-service —— 中文方案里功能最全

- https://github.com/tfcenter/tfcenter-service ｜ 64 star ｜ Apache-2.0
- 定位：免费的内网穿透 + 文件管理软件，支持 **WebDAV 文件管理、本地文件管理、DDNS、socks5/https 代理**，P2P 穿透支持 IPv4/IPv6。
- 适合：想找中文文档、Windows 友好、不想自己写代码的场景。
- **短板**：同样是"穿透到 B 侧"，文件不集中到 A；项目更新节奏与文档质量需要自己评估。

### 4. spianmo/Ferryman —— 有 agent 架构，但方向偏了

- https://github.com/spianmo/Ferryman ｜ 4 star ｜ MIT ｜ C++20 + React
- agent 外连 + 浏览器控制台，含 terminal / files / tasks / 屏幕流。方向是"远程 AI 编程控制台"，文件只是附带能力，不适合作为文件系统的基座。

### 这一轮的结论

| 你想要的三件事 | GitHub 现状 |
|---|---|
| ① 反向接入 | 方案极多，成熟（MeshCentral / chisel / frp / rathole） |
| ② 按需从 B 取件 | 有（MeshCentral、remote-machine-access），但均**不落盘** |
| ③ 集中在 A 上管理 | 有（FileBrowser Quantum、copyparty），但**不会主动去 B 取** |
| ②+③ 同时满足 | **只有 UrBackup，且是快照语义** |

所以"总能找到"这句话对了一半：**架构能找到，成品找不到。** 最省力的路径是拿 `remote-machine-access` 的协议和安全模型做骨架，把它的 relay 从"纯中转"改成"落盘 + 存储目录 + 任务队列"，后面接 FileBrowser Quantum 做管理界面。

## 七、可选落地路线

**路线 A：直接改造 MeshCentral（最快看到效果）**
装好 MeshCentral，C 用 `Files` 标签浏览 B 并取文件。缺点是文件不落盘在 A，需要自己加一个"下载即归档"的钩子。适合先验证网络通路与交互。

**路线 B：拿 remote-machine-access 当骨架改（最省力的自研）**
它的协议、握手、路径沙箱、token 校验都是现成且经过认真设计的，把 relay 从"纯流式中转"升级成"落盘 + 存储目录 + 任务队列"即可，改动集中在服务器侧。注意它没有 LICENSE，只能参照思路重写，不能直接复制代码。

**路线 C：完全自研薄薄一层 + 成熟组件（最贴合需求，推荐）**
A 上用 Go/Node 写一个约千行的服务：WebSocket 指令通道 + 任务队列 + 上传接口 + 存储目录；前端用 FileBrowser Quantum 管 A 的存储，或直接调它的 API。B 的 agent 也是几百行。frp 只在需要时叠加以外。

**路线 D：UrBackup 兜底（要"留档"不要"实时"时）**
如果你真正的诉求是"B 上的文件定期归档到 A，C 能随时取"，UrBackup 开箱即用，不用写代码。代价是失去实时选文件的自由度。

**路线 E：PowerConnect 改（只想快速能用）**
如果你其实可以接受"文件留在 B、A 只做通道"，PowerConnect 是 MIT 协议、中文文档、Node 技术栈，改起来门槛最低。

## 八、几个必须避开的坑

1. **不要再选原版 File Browser** —— 2026 年已归档，JWT 会话无法吊销（登出/改密后旧 token 仍有效），命令执行特性历史漏洞密集。用 Quantum 分支。
2. **B 侧必须设根目录白名单** —— 否则 C 等于拿到了 B 的整个硬盘，`../` 穿越是首要攻击面。
3. **C 的登录态和 B 的设备凭证必须是两套密钥体系** —— 否则拿到前端账号就等于拿到 B。
4. **指令通道和文件通道要分离** —— 大文件传输会阻塞同一条 WebSocket 上的指令与心跳，导致 B 被误判离线。
5. **A 的磁盘是唯一副本** —— 删除操作必须进回收站或二次确认。

## 九、针对「A↔B 单条 WebSocket 控制通道」架构的参考优先级

前提已定：A 通过 WebSocket 控制 B，B 按情况走 HTTP 或 socket 上传，后续还要下发实时指令。这个前提下，参考价值不等于功能相似度，而是**"它有没有解决你接下来一定会撞上的那个问题"**。

### 必读，只有三个

| 项目 | 读它解决什么 | 具体该看的部分 | 不要学的部分 |
|---|---|---|---|
| **remote-machine-access** | 控制通道的骨架：建链、鉴权、消息帧、文件操作 RPC 的粒度与错误语义 | WSS 握手与 token 校验；`list / stat / read / write / delete` 各自的入参与返回；`resolve()` 之后的路径沙箱校验；常量时间 token 比较 | relay 无状态、不落盘；无 LICENSE，只能参照思路重写 |
| **MeshCentral** | 传输层：**怎么在一条长连接上既跑指令又跑文件还不互相堵死** | 文件传输的分块大小、背压控制、进度回传、取消、断点续传；同连接上指令与数据的隔离方式 | 整套设备/用户/AMT 管理模型，重量级，别照搬 |
| **copyparty** | HTTP 上行的工业级做法：断点续传与去重 | 分块上传协议（客户端分块 + SHA-256 校验 + 256KB–4MB 自适应块大小）、重复文件秒传 | 它那套 volumes/permissions 配置体系和偏功能型的 UI |

### 按技术栈选读

| 项目 | 什么时候看 | 看什么 |
|---|---|---|
| **PowerConnect** | A/B 用 Node 写 | 文件模块的路由组织、流式下载（`createReadStream` 直出）、路径限制、移动端 UI |
| **FileBrowser Quantum** | 要做 A 端的文件管理界面 | 列表/搜索/权限/分享的 API 形态与字段设计 |
| **UrBackup** | 要设计落盘后的存储布局 | 快照目录结构、硬链接去重、按客户端分目录的组织方式 |
| **chisel** | 后续要做实时指令 | 它把 **SSH 跑在 WebSocket 上**（`golang.org/x/crypto/ssh` + `gorilla/websocket`），用 SSH channel 做多路复用——这正是"指令与文件流共存"的标准解法 |

### HTTP 还是 socket：不应该是"看情况"，而应该按规则路由

| 场景 | 走什么 | 原因 |
|---|---|---|
| 大文件（>10MB）、需要断点续传 | **HTTP 分片 PUT/POST** | 可分片重试、可多路并发、可被 Nginx/对象存储接管、不占用控制连接、天然幂等 |
| 小文件（配置、日志、截图心跳） | **控制通道内传或短连接** | 省一次握手，延迟低，量大但每个都很小 |
| 需要服务端实时回压/双向流 | **独立的第二条 WebSocket** | 与指令通道物理隔离，互不阻塞 |
| 批量小文件 | **打包后走 HTTP** | 避免 N 次 RPC 往返 |

**核心约束：一条 WebSocket 同时承载实时指令和大文件流，一定会互相阻塞。** 大文件传输期间心跳延迟升高，A 会误判 B 离线；背压处理不当还会把指令队列拖死。解法只有两个：给数据单独开一条连接，或者在一条连接上做多路复用（smux / yamux / SSH channel）。**这是你这个架构里最容易被低估的设计点，先定它，再定其他。**
