# Robot Monitor 部署手册

面向 **Ubuntu 22.04 / 24.04**（Debian 系，systemd + Nginx）。RHEL 系的差异在文末。

约定：

| 角色 | 是什么 | 要装什么 |
|---|---|---|
| **A** | 有公网 IP 的服务器 | `server/` + Nginx + TLS |
| **B** | 内网机器，无公网 IP | robot-backend 的 cloud-agent |
| **C** | 你的浏览器 | 什么都不用装 |

---

## 0. 前置检查

### 0.1 端口

| 端口 | 谁能访问 | 用途 |
|---|---|---|
| **443/tcp** | 公网（浏览器 + 机器侧 cloud-agent） | 全部业务：页面、`/api/*`、`/api/events`（SSE）、`/ws/agent`（控制通道）、`/internal/*`（分片上传） |
| **80/tcp** | 公网 | 只做 ACME 验证 + 301 跳 443。没有域名/证书时可先只开它，但不建议长期 |
| 8000/tcp | **只有本机** | uvicorn，绑 `127.0.0.1:8000`，绝不对公网开放 |

控制通道和上传通道**共用一个 443**，靠路径区分：`/ws/agent` 升级成 WebSocket，
`/internal/*` 是普通 HTTP。这是"控制走 WS、数据走 HTTP"的附带好处——不用为上传
再开端口、再配证书、再加防火墙规则。

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
ss -lntp | grep 8000        # 应为 127.0.0.1:8000，不是 0.0.0.0:8000（8000 不要放行）
```

B 侧不需要任何入站端口：它主动拨出 443。

### 0.2 机器本身

在 A 上确认三件事，缺任何一件后面都会卡住：

```bash
# 1) 有域名并已解析到这台机器（没有域名看文末「没有域名怎么办」）
dig +short files.example.com

# 2) 系统时间正确。TLS 与 token 都依赖时间，偏几分钟就会"证书有效但握手失败"
timedatectl status | grep -i synchronized

# 3) 443 没被别的服务占用
sudo ss -lntp | grep -E ':443|:80' || echo "端口空闲"
```

## 1. 在开发机上构建产物

服务器上没有 Node，前端必须在本地构建好。**在本仓库根目录**执行：

```bash
# 前端产物：server/frontend/dist
cd server/frontend && npm ci && npm run build && cd -
```

拷贝到机器上（`--exclude` 很重要，否则会把开发机的 `.venv` 和 `node_modules` 一起传上去，慢且会覆盖服务器环境）：

```bash
# 代码（server/ 整体，不含 node_modules 与 .venv）
rsync -av --exclude node_modules --exclude .venv --exclude __pycache__ \
      server/ root@A:/tmp/robot-monitor-server/

# 配置模板（deploy/ 在仓库根，不在 server/ 里，要单独传）
rsync -av deploy/ root@A:/tmp/deploy/
```

## 2. 部署 A（服务器）

### 2.1 用户与目录

```bash
sudo useradd -r -s /usr/sbin/nologin robot-monitor
sudo mkdir -p /opt/robot-monitor /var/lib/robot-monitor/{data,storage} /etc/robot-monitor
sudo chown -R robot-monitor:robot-monitor /var/lib/robot-monitor

# 给服务账号一个可写的 HOME：uv 要在这里放缓存目录。
# `useradd -r` 不会创建 home，缺了它 `sudo -u robot-monitor uv sync` 会直接失败。
sudo mkdir -p /home/robot-monitor && sudo chown robot-monitor:robot-monitor /home/robot-monitor
```

### 2.2 代码与依赖

```bash
sudo rsync -a /tmp/robot-monitor-server/ /opt/robot-monitor/
sudo chown -R robot-monitor:robot-monitor /opt/robot-monitor

# uv 装成系统级（systemd 里的服务用户没有自己的 PATH）
curl -LsSf https://astral.sh/uv/install.sh | sh
sudo install -m 755 ~/.local/bin/uv /usr/local/bin/uv

# 装依赖。--frozen 表示严格按 uv.lock，不做二次解析
sudo -u robot-monitor uv sync --project /opt/robot-monitor/backend --frozen
```

装完应该有 `/opt/robot-monitor/backend/.venv/bin/robot-monitor-server`。确认一下：

```bash
ls -l /opt/robot-monitor/backend/.venv/bin/robot-monitor-server
ls -l /opt/robot-monitor/frontend/dist/index.html
```

### 2.3 配置（不含密码）

```bash
sudo install -m 640 -o root -g robot-monitor /tmp/deploy/robot-monitor.env.example \
     /etc/robot-monitor/robot-monitor.env
sudo nano /etc/robot-monitor/robot-monitor.env
```

```ini
ROBOT_MONITOR_HOST=127.0.0.1
ROBOT_MONITOR_PORT=8000

ROBOT_MONITOR_DATA_DIR=/var/lib/robot-monitor/data
ROBOT_MONITOR_STORAGE_DIR=/var/lib/robot-monitor/storage
ROBOT_MONITOR_FRONTEND_DIR=/opt/robot-monitor/frontend/dist

# 上了 HTTPS 必须为 true，否则浏览器会丢弃 Cookie
ROBOT_MONITOR_COOKIE_SECURE=true

# 新设备准入：closed（默认，全部要你在「节点」页点批准）
#              first（空库时第一台免审）/ open（全部免审，仅限完全可信内网）
ROBOT_MONITOR_ENROLL_POLICY=closed

ROBOT_MONITOR_LOG_LEVEL=INFO
```

**这里没有密码哈希**。密码存在 `data/robot-monitor.db` 里，第一次启动时引导设置，
之后用 `robot-monitor-server passwd` 改——改完立即生效，不用重启，也不用动这个文件。

### 2.4 起服务（首次会设置密码）

```bash
sudo cp /tmp/deploy/systemd/robot-monitor-server.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now robot-monitor-server
sudo systemctl status robot-monitor-server --no-pager
```

`serve` 检测到库里还没有密码，会走两条路之一：

**有终端**（手动前台跑）：直接提示你输两次。

**没有终端**（systemd）：生成一个随机密码，写进
`/var/lib/robot-monitor/data/initial-password`（权限 600），日志里只打路径、不打密码：

```bash
sudo cat /var/lib/robot-monitor/data/initial-password
```

登录一次之后这个文件会自动删除。想立刻改掉：

```bash
sudo -u robot-monitor /opt/robot-monitor/backend/.venv/bin/robot-monitor-server passwd
```

本机自检：

```bash
curl -s http://127.0.0.1:8000/api/v1/health
# {"status":"ok","version":"0.1.0","protocol":1,"storage_ready":true,
#  "auth_configured":true,"agents_online":0}
```

`auth_configured` 必须是 `true`——它是查数据库得到的，不是查环境变量。

### 2.5 Nginx + TLS

```bash
sudo apt install -y nginx
sudo cp /tmp/deploy/nginx/robot-monitor.conf /etc/nginx/conf.d/
sudo nano /etc/nginx/conf.d/robot-monitor.conf     # 改 server_name 为上你的域名
sudo nginx -t && sudo systemctl reload nginx

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d files.example.com
```

外网自检：

```bash
curl -s https://files.example.com/api/v1/health
curl -sI https://files.example.com/ | head -3      # 200，content-type: text/html
```

四个专项配置都在 `robot-monitor.conf` 里，不要删：`client_max_body_size 32m`（8MB 分片）、
`/api/events` 关 buffering（SSE）、`/ws/agent` 加 Upgrade 头与长超时、`/internal/` 不缓冲。

## 3. 让机器人接入（默认自动注册）

**不需要手工签 token。** 机器第一次带 `--server` 启动 `cloud-agent` 就会向云端注册，
token 由云端签发并写进凭据文件（0600）——人不经手，也不进 shell history。位置：
`<robot-backend>/.cloud-agent/agents/`（可用 `ROBOT_CLOUD_AGENT_STATE_DIR` 改）。
**一台云端一个文件**，文件名带主机名和地址 hash，换地址不会覆盖，换回去还是原来的
`agent_id`。

机器的启动方式（开发期）：

```bash
cd <robot-backend>
.venv/bin/python -m app.cloud_agent --server https://files.example.com --root /srv/share
```

准入由 `ROBOT_MONITOR_ENROLL_POLICY` 决定：

| 策略 | 行为 |
|---|---|
| `closed`（默认） | 一律转待批准。第一台也一样——不依赖"谁先连上" |
| `first` | 库里一台节点都没有时直接放行；已有节点则转待批准 |
| `open` | 一律放行。只适合完全可信的内网 |

### 需要人工批准时

**在网页里点两下就行**：登录后打开「节点」页，顶部会出现「待批准接入」表格
（主机名、共享目录、来源 IP、申请时间），点 **批准** 或 **拒绝**。批准后 B 在
几秒内自动领到 token 并连上，不用重启，也不用碰命令行。

这张表是 SSE 推的：B 提交申请的那一刻，页面自己就冒出来了，不需要刷新。

想用命令行（或没开浏览器）时：

```bash
# A 上看有哪些待批
sudo -u robot-monitor bash -c '
  set -a; . /etc/robot-monitor/robot-monitor.env; set +a
  /opt/robot-monitor/backend/.venv/bin/robot-monitor-server pending
'
# ID          HOSTNAME   ROOT          FROM         TIME
# 7c1e9d4a..  lab-02     /data/share   10.0.0.42    08-22 18:52

sudo -u robot-monitor bash -c '
  set -a; . /etc/robot-monitor/robot-monitor.env; set +a
  /opt/robot-monitor/backend/.venv/bin/robot-monitor-server approve 7c1e
'
```

ID 可以用前缀（命令行），网页里用的是完整 ID。批准之后 B 会在几秒内自动领到
token 并连上，不需要重启。

### 仍然可以手工签发（可选）

给自动化脚本、或者不想开注册通道时用：

```bash
sudo -u robot-monitor bash -c '
  set -a; . /etc/robot-monitor/robot-monitor.env; set +a
  /opt/robot-monitor/backend/.venv/bin/robot-monitor-server issue-token --name b-office
'
```

输出 `[db] /var/lib/robot-monitor/data/robot-monitor.db` + `agent_id` + `token`。
在机器人的「云端接入」页面填 server + token + agent_id 即可（对应
`POST /api/v1/cloud-link/credentials`），也可以直接用 CLI：
`.venv/bin/python -m app.cloud_agent --server ... --token ... --root ...`。
配合 `ENROLL_POLICY=closed` 就是"完全不开自动注册"。

token 只显示一次（库里只有 sha256）；丢了重签会轮换，旧 token 立即失效。

## 5. 首次使用

1. 浏览器打开 `https://files.example.com`，用 `admin` + 2.3 设的密码登录
2. **节点**：看到 `b-office`，绿灯，共享根目录 `/srv/share`
3. **取件**：选节点 → 展开目录树 → 勾选文件或目录 → 提交取件
4. **任务**：进度条实时走（SSE）。失败会显示原因与错误码
5. **文件库**：按目录浏览 / 搜索 / 打包下载 / 删除（删了就没了）

取一个几百 MB 的文件验证一下真实吞吐，比只看「done」更可靠。

## 6. 验收清单

部署完逐条打勾。每条都能独立暴露一类问题。

| # | 检查 | 命令 / 操作 | 期望 |
|---|---|---|---|
| 1 | 服务在跑 | `systemctl is-active robot-monitor-server` | `active` |
| 2 | 只听本机 | `sudo ss -lntp \| grep 8000` | `127.0.0.1:8000`，**不是** `0.0.0.0` |
| 3 | 只开两个端口 | `sudo ufw status` | 只有 80、443（+ 你的 SSH） |
| 4 | 健康 | `curl -s https://域名/api/v1/health` | `auth_configured: true`，`status: ok` |
| 5 | 匿名被拒 | `curl -s -o /dev/null -w '%{http_code}' https://域名/api/v1/files` | `401` |
| 6 | 登录 | 浏览器登录 | 进到节点页 |
| 7 | 在线 | 节点页 | 先在「待批准接入」点批准，然后绿灯 + 3 秒内 |
| 7b | 准入策略 | 再加一台机器人 | 网页「节点」页出现「待批准接入」，点批准后自动连上（`pending`/`approve` 命令行同理） |
| 8 | 取件 | 取一个文件 | 任务 done，进度 100% |
| 9 | 校验 | `sha256sum /srv/share/某文件` 对比文件库里的 sha256 | 一致 |
| 10 | Range | `curl -r 0-99 https://域名/api/v1/files/<id>/download -o /dev/null -w '%{http_code}'` | `206` |
| 11 | SSE | 停在任务页，另开一个终端取件 | 进度条自己动，不用刷新 |
| 12 | 吊销 | `revoke-token <id>` 后在机器人「云端接入」页点「轮换 token」 | 轮换失败并提示 `revoked`，节点变离线 |
| 12b | 改密码 | `robot-monitor-server passwd` | 旧密码失效，已登录会话被踢下线 |
| 13 | 机器人无入站 | 在外部 `nc -vz 机器人IP 80` | 不通（本来就不该通） |
| 14 | 备份 | `sudo deploy/backup.sh` | 生成 db 与 files 两个 tar.gz |

第 12 条做完，在机器人页面上点「立即注册」或「删除凭据」后再注册：默认策略下
它会进入待批准，`robot-monitor-server pending` 看一眼再 `approve` 即可恢复在线。

## 7. 升级与回滚

### 备份（每次升级前必做）

```bash
sudo ROBOT_MONITOR_DATA_DIR=/var/lib/robot-monitor/data \
     ROBOT_MONITOR_STORAGE_DIR=/var/lib/robot-monitor/storage \
     deploy/backup.sh /var/backups/robot-monitor
```

**不要直接 `cp` SQLite 文件**：WAL 模式下会拿到缺少最近提交的库。脚本里用的是
backup API。产物是 db 与 files 两个 tar.gz。

### 升级 A

```bash
# 1. 先备份（SQLite 不能直接 cp，见 deploy/backup.sh 里的说明）
sudo deploy/backup.sh /var/backups/robot-monitor

# 2. 传新代码（--delete 会删掉服务器上已移除的文件，先确认没有手改过）
sudo rsync -a --delete --exclude .venv /tmp/robot-monitor-server/ /opt/robot-monitor/

# 3. 依赖与重启
sudo -u robot-monitor uv sync --project /opt/robot-monitor/backend --frozen
sudo systemctl restart robot-monitor-server
```

### 升级机器侧

机器侧与云端不在同一个仓库，升级在 `robot-backend` 里做，见它的 `deploy/README.md`。

### 回滚

没有 git 也能回：升级前把整个目录留一份。建议在升级脚本里加：

```bash
sudo cp -a /opt/robot-monitor /opt/robot-monitor.bak.$(date +%F-%H%M)
```

数据库结构目前是纯增量（`CREATE TABLE IF NOT EXISTS`），所以回滚代码不会炸库；
但**回滚前先想清楚有没有写过新表**，没有就可以直接换回去。

## 8. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面 404 / 空白 | `dist` 没构建，或 `ROBOT_MONITOR_FRONTEND_DIR` 指错 | `ls dist/index.html`；日志里有一行 `前端产物不存在` |
| `auth_configured: false`，登录 503 | 库里还没有密码 | `serve` 启动时会引导；或手动 `robot-monitor-server passwd` |
| 忘了密码 | —— | `robot-monitor-server passwd`（会先要求当前密码）；实在不行删掉库里 `admin_user` 那一行再 `passwd` |
| 登录 429 | 限流（默认 10 次/分钟/IP） | 等一分钟；或调 `ROBOT_MONITOR_LOGIN_RATE_LIMIT_PER_MINUTE` |
| 节点一直离线 | token 错/被吊销/签进了别的库 | 机器人「云端接入」页会显示 `unauthorized` 与原因；再看云端日志有没有 `agent ... online` |
| B 卡在"等待批准" | 默认策略 `closed`，所有新设备都要批 | 打开 A 的「节点」页，在「待批准接入」里点 **批准**；没看到就点右上角刷新 |
| 节点偶尔离线又回来 | 反代把 WS 掐了 | `robot-monitor.conf` 的 `/ws/agent` 必须有 Upgrade + `proxy_read_timeout 3600s` |
| 上传 413 | Nginx 默认 body 上限 1MB | `client_max_body_size 32m` |
| 上传 401 | cloud-agent 推的 HTTP base 不对 | 它的 `server` 必须是 `https://域名`，别带 `/ws/agent` 之外的路径 |
| 进度条不动，刷新后又是对的 | SSE 被缓冲 | `/api/events` 要 `proxy_buffering off` + `X-Accel-Buffering: no` |
| `database is locked` | 起了多个 uvicorn worker | 只允许 1 个；`workers=1` 写死在代码里，别用 `--workers` 覆盖 |
| 任务失败 `checksum_mismatch` | 文件在传的过程中被改了 | 正常保护。重取即可；日志文件建议改完再取 |
| 任务失败 `size_changed` | 同上，或机器人上是正在写的日志 | 同上 |
| `只支持 Linux，当前平台是 win32` | 平台门禁 | 预期行为，cloud-agent 必须 Linux |
| `curl` 能通但浏览器报证书错 | 证书只配了域名没配 IP，或用了 IP 访问 | 用域名访问 |

日志位置：

```bash
sudo journalctl -u robot-monitor-server -n 100 --no-pager
```

机器侧日志在机器人上：`logs/cloud_agent.log`，或直接用「云端接入」页的日志面板。

## 附：没有域名怎么办

三种选择，按推荐度排序：

1. **搞一个域名**（最省事）。几块钱一年的域名 + certbot 全自动续期。
2. **自签证书**：cloud-agent 把 `verify_tls` 设为 false 跳过校验，但浏览器会红警告，
   且这等于放弃了「中间人无法窃取 token」这条保证。只适合临时验证。
3. **明文 HTTP**：能跑，但 token 会以明文经过链路（`Authorization` 头）。
   **只在完全可信的内网、且有 deadline 的情况下用**，并且尽快换成 TLS：

   ```ini
   ROBOT_MONITOR_AGENT_SERVER=http://A的IP:80
   ROBOT_MONITOR_COOKIE_SECURE=false
   ```

## 附：RHEL / Rocky / AlmaLinux

差异只有三处：

```bash
# 1) 防火墙
sudo firewall-cmd --permanent --add-service=http --add-service=https
sudo firewall-cmd --reload

# 2) SELinux 默认禁止反代连本地端口
sudo setsebool -P httpd_can_network_connect 1

# 3) Nginx 配置放这里
sudo cp deploy/nginx/robot-monitor.conf /etc/nginx/conf.d/
```

其余步骤（uv、systemd、certbot 用 `python3-certbot-nginx`）完全一致。
